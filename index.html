Complex Troubleshooting in ADA Post-Upgrade

Successfully resolved multiple critical errors that emerged after the Angular upgrade, requiring deep debugging across authentication, security headers, and dependency management. This work was essential to getting the application functional again in the development environment.

NullInjection Error Resolution (Primary Challenge)
  • Error Context: NullInjector error occurred post-upgrade, indicating Angular's dependency injection system couldn't find required providers. This was blocking the entire application from loading properly and manifested as a blank screen with console errors.
  • Impact: Application completely non-functional, affecting all development and testing work. This was a blocker for the entire team's progress on ADA features.
  • First Approach (Keycloak Configuration):
    • Initially suspected authentication provider issues in Keycloak based on error stack trace
    • Attempted to reconfigure client scopes and mappers in Keycloak admin console
    • Verified token endpoints and OAuth flows were correctly configured
    • Checked realm settings and client secret configurations
    • This approach did not resolve the NullInjector error, indicating the root cause was elsewhere in the stack
    • Time invested: ~4 hours debugging authentication configurations
  • Second Approach (Content Security Policy Analysis):
    • Discovered that strict CSP headers in Nginx were blocking necessary inline scripts and external resources
    • The application needs Font Awesome icons and Google Fonts to render the UI properly
    • CSP violations were preventing Angular from bootstrapping correctly, which manifested as the NullInjector error
    • Used browser DevTools Network and Console tabs to identify blocked resources
  • Detailed Troubleshooting Steps:
    1. Removed nonce directive and tested with only 'unsafe-inline' (necessary for Angular's dynamic script injection during bootstrap)
    2. Tried using 'unsafe-inline' for both script-src and style-src to allow inline styling that Angular generates
    3. Added stylesheet URLs specifically into HTML header tags as fallback loading mechanism
    4. Explicitly whitelisted external CDN sources (Font Awesome at use.fontawesome.com, Google Fonts at fonts.googleapis.com and fonts.gstatic.com)
    5. Tested each change incrementally to isolate which specific directive was causing the bootstrap failure
    6. Verified changes using browser DevTools console to track CSP violations in real-time
    7. Validated that removing each restriction actually fixed the corresponding error without introducing new ones
  • Configuration Changes Made:
    • Original restrictive policy:
      add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self';" always;
    • Updated to allow necessary resources:
      add_header Content-Security-Policy "default-src 'self'; \ script-src 'self' 'unsafe-inline' https://use.fontawesome.com; \ style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; \ font-src 'self' https://fonts.gstatic.com; \ connect-src 'self' [keycloak-endpoint];" always;
    • This balances security with functionality by allowing only specific trusted external sources while maintaining protection against XSS attacks
    • Documented the rationale for each 'unsafe-inline' usage for future security audits
  • Additional Fixes Required:
    • Updated Keycloak realm configurations to match the most recent version (realm names changed from legacy format to new naming convention)
    • Modified client IDs and redirect URIs to align with new authentication flow
    • Removed unused imports that were causing circular dependencies (specifically in auth.service.ts and app.module.ts)
    • Downgraded Apollo Client from v3.8 to v3.7.x due to breaking changes in the newer version's cache implementation that wasn't compatible with our GraphQL setup
    • Verified all authentication flows (login, logout, token refresh) worked correctly after changes
    • Tested with multiple user roles to ensure permissions were preserved
  • Root Cause Analysis: The NullInjector error was a symptom, not the root cause. The actual issue was that Angular's bootstrapping process was silently failing due to CSP violations, which then cascaded into dependency injection failures. This taught me the importance of checking browser console for CSP violations when debugging mysterious Angular errors.
  • Key Learning: NullInjector errors can have multiple root causes beyond missing providers. Security policies like CSP can prevent Angular from bootstrapping properly, leading to confusing error messages. Always check browser console for CSP violations first, then work backwards from there. Also learned that error messages in Angular can be misleading – the stack trace pointed to DI issues, but the real problem was in the infrastructure layer.
  • Total Time: ~2 days of debugging and testing to fully resolve

This process took about a full week of focused effort and taught me so much about dependency management and backward compatibility.
  • Installation and Core Updates:

    • Cross-referenced with ACL (Angular Component Library) dependency versions to ensure compatibility across our shared component system
    • Added xlsx dependency for Excel file handling functionality (new feature requirement)
    • Package.json Version Symbols:
      • ^ (caret): Allows updates to the most recent compatible version within the same major version. Example: ^16.2.0 will update to 16.9.9 but not 17.0.0. Good for getting bug fixes and minor features automatically.
      • ~ (tilde): Restricts updates to only patch releases within the same minor version. Example: ~16.2.0 will update to 16.2.9 but not 16.3.0. Provides more control and stability for critical dependencies.
      • I used tilde for core Angular packages to avoid unexpected breaking changes, and caret for utility libraries where we wanted automatic updates.
  • Specific Package Updates:
    • Upgraded @fortawesome/angular-fontawesome from v0.11 to v0.13 to support Angular 16's new injection system
    • Updated @angular/animations to match core Angular version (critical for Material components)
    • RxJS stayed at v7 (no upgrade needed, but verified compatibility)
    • Updated Angular Material to v16 (required multiple template changes)

Understanding cURL Requests (New Technical Skill)
  • What is cURL? cURL (client for URLs) is a command-line tool and library for transferring data using various network protocols. It's essential for testing APIs, debugging network issues, and automating data transfers.
  • Core Functionality:
    • Retrieves data like fetching web pages, JSON responses, images, and files
    • Supports HTTP methods: GET (retrieve data), POST (send data), PUT (update resources), PATCH (partial updates), DELETE (remove resources)
    • Handles authentication (Basic Auth, Bearer tokens, OAuth)
    • Custom headers, cookies, and request bodies
  • Practical Examples I Used:
    • Testing API endpoints:
      curl -X GET https://api.lyric.local/v1/users \ -H "Authorization: Bearer [token]" \ -H "Content-Type: application/json"
    • Checking response headers:
      curl -I https://ada.lyric.local
    • POST request with JSON body:
      curl -X POST https://api.lyric.local/v1/accounts \ -H "Content-Type: application/json" \ -d '{"name": "Test Account", "type": "checking"}'
  • Debugging API Endpoints:
    • Used cURL to test Keycloak token endpoints and verify JWT token issuance
    • Validated that Nginx reverse proxy was correctly forwarding requests to backend services
    • Tested BKS hub endpoints to ensure routing was working after configuration changes
    • Debugged CORS issues by examining response headers
    • Verified that SSL certificates were properly configured
  • Challenges and Learnings:
    • Initially struggled with authentication because I wasn't including the correct Bearer token format
    • Learned to use -v (verbose) flag to see full request/response cycle for debugging
    • Understanding of how headers affect API behavior (Content-Type, Accept, Authorization)
    • Overall it was challenging because I was learning so many new concepts simultaneously (HTTP protocol, REST APIs, authentication flows)
  • What I Wish I'd Done Differently: I wish I had created an isolated testing environment (maybe using Docker containers or Postman collections) where I could experiment with API endpoint connections away from the main codebase. This would have let me understand the API contracts better before integrating them into the application. I was essentially learning by debugging production-like code, which was stressful.
  • Tools Comparison:
    • cURL: Great for quick command-line testing, scriptable, available everywhere
    • Postman: Better UI, collection management, but requires GUI
    • Insomnia: Similar to Postman, good for GraphQL
    • I'm now comfortable with all three and know when to use each

CI/CD Pipeline and DevOps Practices

Gained comprehensive understanding of our development and deployment pipeline, from local development through production deployment. Learned how automated testing, security scanning, and quality gates ensure code quality before reaching production.

Pipeline Stages and Flow
  • Local Development:
    • Developer writes code and commits to feature branch
    • Pre-commit hooks run linting (ESLint) and formatting (Prettier)
    • Local tests run with ng test (Jest for unit tests)
  • Pull Request Creation:
    • PR triggers GitHub Actions workflow automatically
    • Branch protection rules require passing checks before merge
    • Automated code review checks (linting, formatting, test coverage)
  • Continuous Integration (CI):
    • Build Stage: Compiles TypeScript, bundles assets, optimizes for production
    • Test Stage: Runs unit tests, integration tests, generates coverage report
    • Security Scanning: CodeQL for security vulnerabilities, SonarQube for code quality
    • Quality Gates: Must meet minimum thresholds for test coverage (>80%), code quality (A rating), security (no high/critical issues)
  • Quality Gates Deep Dive:
    • SonarQube Checks:
      • Code coverage: Must maintain >80% line coverage
      • Code smells: Maintainability issues that make code harder to change
      • Bugs: Logic errors detected by static analysis
      • Security hotspots: Code patterns that might be vulnerable
      • Technical debt: Estimated time to fix all issues
    • CodeQL Security Scanning:
      • Scans for SQL injection, XSS, CSRF vulnerabilities
      • Checks for hardcoded credentials and secrets
      • Identifies insecure cryptography usage
      • Detects potential path traversal issues
    • Failed Quality Gate Experience: During Angular upgrade, my initial PR failed quality gates due to increased cyclomatic complexity in upgraded files and reduced test coverage from deprecated test utilities. Had to refactor code and update tests to meet thresholds.
  • Continuous Deployment (CD):
    • Development Environment: Automatic deployment on merge to develop branch
    • Staging Environment: Manual trigger for QA testing
    • Production Environment: Requires approval from team lead, deployed during maintenance windows
  • Deployment Strategy:
    • Blue-green deployment: Two production environments, switch traffic after verification
    • Allows instant rollback if issues detected
    • Zero-downtime deployments
    • Automated health checks before switching traffic
  • Rollback Procedures:
    • Keep previous Docker images tagged and ready
    • Database migrations are reversible with down scripts
    • Configuration changes are versioned and can be reverted
    • Learned to prepare rollback plan before any production deployment
  • Monitoring and Alerts:
    • Application performance monitoring (APM) tracks response times and error rates
    • Logs aggregated in centralized logging system (ELK stack)
    • Alerts configured for critical errors, high latency, and service downtime
    • On-call rotation for handling production incidents
Configuration Management Across Environments
  • Environment-Specific Configuration:
    • Development: Relaxed security, verbose logging, mock data services
    • Staging: Production-like config, anonymized production data, full monitoring
    • Production: Strict security, minimal logging, real user data
  • Environment Variables:
    • API endpoints, database connection strings, Keycloak realm URLs
    • Feature flags for gradual rollout (controlled by environment config)
    • Secrets management using GitHub Secrets and environment-specific vaults
    • Learned to never commit secrets to Git (use .env files in .gitignore)
  • Keycloak Configuration Integration:
    • Different realms for each environment (dev, staging, prod)
    • GIDS Keycloak for employee authentication in internal tools
    • BKS Keycloak for customer-facing banking application
    • Environment files control which Keycloak instance to use
    • Client credentials and secrets stored securely per environment
  • OAuth 2.0 and OpenID Connect Flows:
    • Authorization Code Flow for web applications (most secure)
    • Implicit Flow (deprecated, not used due to security concerns)
    • Client Credentials Flow for server-to-server communication
    • PKCE (Proof Key for Code Exchange) for mobile/SPA security
    • Understanding token lifetimes (access tokens: 5 min, refresh tokens: 30 days)
  • JWT Token Structure:
    • Header: Algorithm and token type
    • Payload: User claims (user ID, roles, permissions, expiration)
    • Signature: Ensures token hasn't been tampered with
    • Learned to decode JWTs using jwt.io for debugging
    • Verified token validation logic in backend services
GitHub Actions Workflow Insights
  • Workflow File Structure:
    • YAML files in .github/workflows/ directory
    • Trigger conditions (on push, pull_request, schedule, manual)
    • Jobs run in parallel or sequentially with dependencies
    • Steps within jobs execute commands or use actions from marketplace
  • Common Actions Used:
    • actions/checkout: Clones repository
    • actions/setup-node: Sets up Node.js environment
    • actions/cache: Caches npm dependencies for faster builds
    • github/codeql-action: Runs security scanning
    • SonarSource/sonarcloud-github-action: Code quality analysis
  • Optimization Techniques:
    • Caching node_modules reduces install time from 3 minutes to 30 seconds
    • Matrix builds for testing across multiple Node versions
    • Conditional steps that only run when relevant files change
    • Artifact uploads for build outputs and test reports
